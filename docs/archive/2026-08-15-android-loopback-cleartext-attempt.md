# Android loopback cleartext config — unlanded attempt, 2026-08-15

> **WHAT THIS IS.** A complete, working implementation that was never committed to a branch, never pushed and never opened as a PR.
> It is archived here because it existed only as uncommitted files in a scratch worktree, where any cleanup would have destroyed it without trace.
>
> **STATUS: OBSOLETE. DO NOT APPLY THIS AS WRITTEN.**
> It permits cleartext HTTP to `localhost`, `127.0.0.1` and `10.0.2.2` only, which unblocks an emulator talking to a mock server and does not help a single real user.
> The defect it was meant to serve is #727, where a physical device fails against a LAN address such as `192.168.68.102` — an address this config still denies.
>
> **The premise was also wrong.** It was built to unblock Android E2E, on the diagnosis that the Maestro flows were failing because release builds deny cleartext.
> They were not: `${E2E_MOCK_SERVER_URL}` was never substituted, so the app dialled the literal host `undefined` and no request left the process. That was fixed in #735.
>
> **What is still true and worth keeping** is in "Findings that outlived the code" at the end. Read that section; treat the code as reference only.

## Why it is archived rather than deleted

The mechanism it demonstrates is sound and was verified into a shipped artifact, so the next person to implement #727's policy decision should not have to rediscover it.
Two of its design decisions are non-obvious and cost real time to establish.

## `plugins/withAndroidLoopbackCleartext.js`

```js
// Lets the *release* APK talk to the Maestro mock server over plain HTTP.
//
// Cleartext is denied by default at targetSdkVersion >= 28, and the
// `usesCleartextTraffic="true"` in android/app/src/debug/AndroidManifest.xml
// lives in a build-type source set, so it is never merged into a release
// build. Android E2E runs `assembleRelease` against http://10.0.2.2:7071, so
// every flow that walks onboarding fails at the handshake.
//
// Two deliberate limits:
//   * the config is written into the `release` source set only, so debug and
//     debugOptimized keep their blanket cleartext and local dev is untouched;
//   * it permits three hosts — localhost, 127.0.0.1 and 10.0.2.2 — and denies
//     everything else, so the shipped APK gains only traffic that cannot leave
//     the device (10.0.2.2 is the Android emulator's alias for its host).

const fs = require('fs');
const path = require('path');

const expoPkgPath = require.resolve('expo/package.json');
const configPluginsEntry = require.resolve('@expo/config-plugins', { paths: [expoPkgPath] });
const { withDangerousMod } = require(configPluginsEntry);

const NETWORK_SECURITY_CONFIG = `<?xml version="1.0" encoding="utf-8"?>
<!-- Generated by plugins/withAndroidLoopbackCleartext.js -->
<network-security-config>
    <base-config cleartextTrafficPermitted="false" />
    <domain-config cleartextTrafficPermitted="true">
        <domain includeSubdomains="false">localhost</domain>
        <domain includeSubdomains="false">127.0.0.1</domain>
        <domain includeSubdomains="false">10.0.2.2</domain>
    </domain-config>
</network-security-config>
`;

const RELEASE_MANIFEST = `<manifest xmlns:android="http://schemas.android.com/apk/res/android">
    <!-- Generated by plugins/withAndroidLoopbackCleartext.js -->
    <application android:networkSecurityConfig="@xml/network_security_config" />
</manifest>
`;

const withAndroidLoopbackCleartext = (config) =>
  withDangerousMod(config, [
    'android',
    (cfg) => {
      const releaseSrc = path.join(cfg.modRequest.platformProjectRoot, 'app/src/release');
      fs.mkdirSync(path.join(releaseSrc, 'res/xml'), { recursive: true });
      fs.writeFileSync(path.join(releaseSrc, 'AndroidManifest.xml'), RELEASE_MANIFEST);
      fs.writeFileSync(
        path.join(releaseSrc, 'res/xml/network_security_config.xml'),
        NETWORK_SECURITY_CONFIG,
      );
      return cfg;
    },
  ]);

module.exports = withAndroidLoopbackCleartext;
```

## `__tests__/unit/scripts/android-cleartext-policy.test.js`

```js
/**
 * @jest-environment node
 *
 * The Android release APK must reach the Maestro mock server over plain HTTP
 * and nothing else.
 *
 * `android:usesCleartextTraffic="true"` lives in android/app/src/debug/, a
 * build-type source set, so it is never merged into a release build. With
 * targetSdkVersion 36 the platform default is cleartext denied, which is why
 * CI run 31864692406 failed 12 of 15 flows: every one of them starts with
 * setup.yaml, whose handshake against http://10.0.2.2:7071 was blocked inside
 * the app before it reached the network.
 *
 * The release source set now carries a network security config. Both halves
 * have to agree — the manifest attribute without the resource fails to build,
 * the resource without the attribute is inert — so both are asserted, plus the
 * app.json registration that keeps `expo prebuild` from dropping them.
 */

'use strict';

const fs = require('fs');
const path = require('path');

const ROOT = path.resolve(__dirname, '../../..');
const RELEASE_SRC = path.join(ROOT, 'android/app/src/release');
const RELEASE_MANIFEST = path.join(RELEASE_SRC, 'AndroidManifest.xml');
const NETWORK_CONFIG = path.join(RELEASE_SRC, 'res/xml/network_security_config.xml');
const APP_JSON = path.join(ROOT, 'app.json');

/**
 * Resolve a host against the config the way Android does: the most specific
 * matching <domain> wins, otherwise <base-config> decides.
 */
function isCleartextPermitted(xml, host) {
  const domainConfigs = xml.match(/<domain-config[\s\S]*?<\/domain-config>/g) ?? [];
  for (const block of domainConfigs) {
    const domains = [...block.matchAll(/<domain[^>]*>([^<]+)<\/domain>/g)].map((m) => m[1].trim());
    if (domains.includes(host)) {
      return /cleartextTrafficPermitted="true"/.test(block.match(/<domain-config[^>]*>/)[0]);
    }
  }
  return /<base-config[^>]*cleartextTrafficPermitted="true"/.test(xml);
}

describe('Android release cleartext policy', () => {
  const config = fs.readFileSync(NETWORK_CONFIG, 'utf8');

  it.each(['10.0.2.2', 'localhost', '127.0.0.1'])('permits cleartext to %s', (host) => {
    expect(isCleartextPermitted(config, host)).toBe(true);
  });

  it.each(['example.com', 'api.threadbase.dev', '192.168.1.10'])(
    'still forbids cleartext to %s',
    (host) => {
      expect(isCleartextPermitted(config, host)).toBe(false);
    },
  );

  it('wires the config into the release manifest', () => {
    const manifest = fs.readFileSync(RELEASE_MANIFEST, 'utf8');
    expect(manifest).toContain('android:networkSecurityConfig="@xml/network_security_config"');
  });

  // A blanket opt-in would make every assertion above pass and still ship
  // cleartext to the whole internet.
  it('does not fall back to blanket cleartext in the release manifest', () => {
    const manifest = fs.readFileSync(RELEASE_MANIFEST, 'utf8');
    expect(manifest).not.toContain('usesCleartextTraffic');
  });

  it('registers the plugin that regenerates both files on prebuild', () => {
    const appJson = JSON.parse(fs.readFileSync(APP_JSON, 'utf8'));
    const names = appJson.expo.plugins.map((entry) => (Array.isArray(entry) ? entry[0] : entry));
    expect(names).toContain('./plugins/withAndroidLoopbackCleartext');
  });
});
```

## Findings that outlived the code

These are the parts worth carrying into whatever implements #727. They are properties of Android and of this repo, not of the discarded allowlist.

**A network security config overrides `usesCleartextTraffic` entirely.**
Putting one in `src/main/` would silently revoke the blanket cleartext that `src/debug/` and `src/debugOptimized/` rely on, breaking local development in a way that would look unrelated.
That is why the config went in the `release` source set. Any future version has the same constraint.

**A hand edit under `android/` is not durable.**
`android/` is committed, so an edit survives day to day, but `npx expo prebuild` regenerates the tree and drops it without a word.
An Expo config plugin that writes the files is the form that survives; committing both the plugin and its output, with a test asserting the plugin is registered, keeps the two from drifting apart.

**Android's `<domain>` matching is hostname-based and has no CIDR support.**
"Permit cleartext for private ranges only" cannot be expressed declaratively.
The realistic options are blanket cleartext in `base-config`, per-host entries, requiring HTTPS, or a runtime trust manager — and the last is a larger hazard than the thing it guards.

**The mechanism reaches the shipped artifact, and that was verified rather than assumed.**
`aapt2 dump xmltree` on the R8'd, resource-shrunk `app-release.apk` resolved `networkSecurityConfig` to the real XML tree, and a release build carrying it completed a pair handshake over plain HTTP to `10.0.2.2`.
So a release build does reach a cleartext host when the config permits it. That is the positive control for #727's mechanism; it says nothing about which hosts *should* be permitted.

**The policy question is not a build question.**
A security review on 2026-08-15 recommended `cleartextTrafficPermitted="true"` in `base-config` rather than requiring HTTPS, on the grounds that this app exists to reach servers the user runs themselves.
Requiring TLS on a home server — self-signed certificate plus a user-added trust anchor to reach a machine in the same room — does not harden that flow so much as delete it, and pushes users onto the tunnel, where traffic passes through a third party in plaintext by design.
If that direction is taken it travels with three conditions: `http://` servers marked as unencrypted persistently rather than behind a dismissible warning, application-layer encryption named as the actual protection, and the decision written down so the next reader of the manifest does not "fix" it.
