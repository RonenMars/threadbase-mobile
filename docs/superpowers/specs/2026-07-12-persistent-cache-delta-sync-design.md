# Persistent cache + cursor-based delta sync (mobile phase 2)

**Date:** 2026-07-12
**Status:** Design approved.
**Server-side design (context):** [tb-streamer PR #197](https://github.com/RonenMars/threadbase-streamer/pull/197)
**Scope:** items 1, 2, 4, 5 from the session prompt — durable store, delta-on-open, retry hygiene, id unification. All work against today's server. Item 3 (WS resume-by-`seq`) is explicitly out of scope here; it needs streamer PR 2 deployed and ships as a separate follow-up PR.

## 1. Acceptance bar

On any conversation open — background→foreground resume, cold app start, or opening a conversation whose session ended — the app renders instantly from its on-device store, sends its last message cursor to the server, and receives only the delta. It never re-downloads history the device already has.

## 2. Audit correction (2026-07-12)

The session prompt's audit was written against an earlier state of the codebase and drifted in one important way: `hooks/useConversations.ts` already has a working forward-cursor pagination lane — `after_index` request param, `has_more_newer`/`next_after_index` in `ConversationMessagePagination`, and a `{ after: number }` `pageParam` branch wired into `getPreviousPageParam` (`useConversations.ts:198-208, 326, 359-364, 425-428`). It is reachable only from an **anchored** first page (search-result jump), never from the plain tail view. This design extends that existing lane rather than building forward-cursor fetching from scratch.

All other audit claims in the session prompt were verified accurate as of 2026-07-12: `QUERY_GC_TIME` 5 min + `staleTime: 0` (`services/query-client.ts:9,41`), `firstPageEtags` module-level in-memory (`useConversations.ts:334`), the three `invalidateQueries` call sites in `useConversationStream.ts` (lines 72, 90, 102), the 8s/15s `AbortController` timeouts in `api-client.ts` (lines 34-37), uuid-only dedup in `LiveConversationView.tsx` (lines 87-90), and no existing `seq` handling anywhere in WS code.

One additional gap the original audit missed: `app/_layout.tsx:347` sets `PersistQueryClientProvider`'s `maxAge: 1000 * 60 * 60 * 24` (24h). This is a global ceiling on the whole persisted snapshot, independent of per-query `gcTime`. Raising `'conversation'`'s `gcTime` to 7 days is inert unless `maxAge` also moves to ≥7 days — a kill+relaunch on day 2 would still cold-fetch even with the per-query change in place.

This design went through five review rounds after the initial draft, which together caught eight load-bearing defects before any code was written: §3.2's trigger mechanism (dead `initialPageParam`), §3.3's automatic-refetch conflict, §3.2's 304 assumption against the real server contract, §3.2's one-shot latch (would have silently broken every foreground resume after the first), §3.3's `invalidateQueries` still causing full chain replays despite the refetch-flag changes (RQ v5's `refetchType: 'active'` default), an unspecified cross-hook wiring gap (`useConversationStream` cannot call `fetchPreviousPage()` on a `useConversation` instance it has no reference to — resolved in §3.3 by lifting all triggering into `useConversation` itself), a non-draining delta (`msg_limit=80` bounding each hop meant a backlog over 80 messages left a permanent gap after a single trigger — resolved in §3.2 by draining sequential `after_index` pages until `has_more_newer` is false or a page comes back empty), and an unspecified "no-op merge" for empty-200 (RQ's `useInfiniteQuery` always appends whatever the `queryFn` returns, with no supported way to decline — resolved in §3.2 by a strip-after-resolve mechanism in the trigger effect). The corrections are folded into the sections below; nothing here reflects any broken intermediate draft.

## 3. Architecture

### 3.1 Durable retention (item 1)

- Add a per-root `gcTime` override so the `'conversation'` query root persists 7 days while other roots (`session`, `project`, `serverInfo`) keep their current 5-minute default. React Query's `gcTime` is set per-query via `queryOptions`/hook config, not globally — `useConversation`'s `useInfiniteQuery` call gets an explicit `gcTime: SEVEN_DAYS` alongside its existing `staleTime`.
- Raise `PersistQueryClientProvider`'s `maxAge` (`app/_layout.tsx:347`) from 24h to 7 days to match. This is a global change (affects the whole persisted snapshot's outer bound), but every other persisted root already tolerates shorter effective retention via its own `gcTime`, so widening the outer ceiling doesn't change their behavior — `gcTime` remains the tighter bound for everything except `'conversation'`.
- **Scope: tail query only.** Only the plain `['conversation', serverId, id]` queryKey gets the 7-day `gcTime`. Anchored windows (`['conversation', serverId, id, 'anchor-${anchorIndex}']`, `useConversations.ts:349`) keep the existing 5-minute default — they're navigation artifacts scoped to a specific search jump, non-resumable by cursor, and never read by the delta-on-open flow. Persisting them 7 days would be pure AsyncStorage bloat (120 messages per window × every search jump ever made) with no consumer. Implementation: branch the `gcTime` value on whether `anchorIndex` is set in `useConversation`'s hook body.
- **ETag map** (`firstPageEtags`, `useConversations.ts:334`) becomes durable via a dedicated AsyncStorage entry (`threadbase-etag-cache-v1`), independent of the React Query persist cycle: read once at module init (hydrate the `Map` before first use), written back (debounced) on every `set`/`delete`. Kept separate from `queryPersister` because its lifecycle (a tiny per-conversation string) isn't really a query-cache concern and shouldn't be tied to `persistBuster`/`maxAge` semantics that exist for message payloads.
- **Cursor is derived, not separately persisted.** `lastMessageIndex` for a conversation = `max(message_index)` across the rehydrated tail query's cached pages, computed at read time (not stored). This keeps a single invariant: cached history exists → cursor exists; history was GC'd or never fetched → no cursor → plain tail fetch. A separately-persisted cursor value could outlive its backing data (cursor with nothing to merge onto), which is strictly worse than falling back to a full fetch.

### 3.2 Delta-on-open (item 2)

Extend `useConversation`'s `ConversationPageParam` union with a fourth shape: `{ resume: number }`, alongside the existing `-1 | number | { after: number }`.

**Why not `initialPageParam`:** React Query only consults `initialPageParam` when a query starts from an empty cache. When cached pages already exist (the rehydrated-from-disk case — the *only* case where a derived cursor exists), a refetch replays existing pages using each page's own stored `pageParam`, and `initialPageParam` is never consulted. So a `{ resume }` `initialPageParam` is dead in both directions: cursor exists ⟹ cache non-empty ⟹ `initialPageParam` ignored; cache empty ⟹ no cursor ⟹ plain `-1`. The trigger must be an explicit fetch call, not the initial-param.

- **Trigger — owned entirely by `useConversation`, four sources:** mount, `AppState` foreground transitions, and (per §3.3) the WS `connected` transition and `running→not-running` transition. All four funnel through one effect inside `useConversation`: if a derived cursor exists for this `serverId/id` (per §3.1), no `anchorIndex` is set, and the module-level per-`queryKey` guard (§3.3) isn't currently blocking, call `query.fetchPreviousPage({ cancelRefetch: false })` (the same handle already exposed as `fetchNewerPage`, `useConversations.ts:456`) with `getPreviousPageParam` (next bullet) resolving to `{ resume: cursor }`. Cached pages render immediately on mount before this fetch resolves — that satisfies "renders instantly, then fetches the delta." This is a **separate, explicit** effect — it does not reuse `app/conversation/[id].tsx`'s existing scroll-driven `fetchNewerPage()` call (`:509-520`, gated on `userHasScrolled.current && nearBottom`, which serves anchored-window backfill and is orthogonal to this trigger; see the Scroll handler bullet below). WS-driven triggering requires `useConversation` to observe WS status as an **observer, never an owner** — it subscribes to the existing per-`serverId` WS client's status/event stream (the same one `useConversationStream` already reads via `wsManager`), filtered to `connected` transitions and this conversation's `running→not-running` transition; it never creates, manages, or assumes existence of a connection. If no socket exists for the server, the subscription is simply inert. `useConversationStream` itself sheds all three of its former `invalidateQueries` call sites (`:72`, `:90`, `:102`) — it becomes purely the live-overlay hook (parse WS lines, `seenIds`, expose `liveMessages`) and never touches the conversation query cache.
- **`getPreviousPageParam` extension:** today it only returns non-`undefined` for anchored pages carrying `has_more_newer` (`useConversations.ts:425-428`). Add a branch, evaluated *after* the existing one — the existing `has_more_newer`/`next_after_index` check on the current newest page (`first.message_pagination`) always wins when present, because it means the server already told us exactly where to continue; the new `{ resume }` branch is a fallback for when that information doesn't exist yet (the newest cached page is plain REST/tail data with no `has_more_newer` field at all — every `after_index` response, including the first delta hop, always carries it). Concretely: for the plain tail view, if the existing branch returns `undefined` and a derived cursor exists, return `{ resume: derivedCursor }` — recomputed on every call, not latched. No one-shot "return once then `undefined`" gating: the cursor advances as merges land (§3.1), so each future foreground/mount/WS trigger must be able to resume from the *current* cursor, including the case where a delta was empty (cursor unchanged, but new messages can still arrive later and must be fetchable on the next trigger). Loop prevention comes entirely from the explicit-trigger design (§3.2's Trigger bullet, plus the module-level per-`queryKey` guard in §3.3), not from starving the param. `hasNewerPage` therefore stays `true` on the tail view whenever a cursor exists, which is correct — it always *can* be asked to check for more.
- **Drain loop — a single delta hop is not enough.** `msg_limit=80` bounds each `after_index` window; a conversation that accumulated more than 80 new messages while the app was backgrounded would otherwise leave a permanent gap after one hop (trigger already fired, 5s guard blocks immediate re-trigger, no other caller exists to pick up the rest — the gap only heals 80-at-a-time across future opens, and meanwhile the WS live overlay shows "now" while history ends 80 messages short). The trigger effect (§3.3) must drain fully: after a non-empty delta resolves, if the merged page's `message_pagination.has_more_newer === true`, immediately call `fetchPreviousPage()` again — this hits the *existing* `has_more_newer` branch above (not a second `{ resume }` hop), fetching `next_after_index` onward. Repeat until either `has_more_newer === false` or an empty-200 page is returned (checking both, belt-and-braces, against a server that might report `has_more_newer` inconsistently on an empty tail). Each iteration is one bounded 80-message page — a 200-message backlog is 3 sequential requests, no artificial cap needed beyond what `has_more_newer`/empty-200 already provides.
- **Scroll handler must be explicitly gated to anchored views.** `hasNewerPage` being permanently `true` on the tail view means `app/conversation/[id].tsx`'s scroll-driven `fetchNewerPage()` call (`:509-520`) is now a second, uncoordinated caller of the same handle the mount/foreground/WS triggers use — not "inert in practice" as originally assumed, but a real second entry point once `hasNewerPage` no longer goes false. Two problems if left unguarded: (1) it would issue redundant `after_index` delta fetches on the tail view whenever the user scrolls near the bottom, outside the intended trigger design; (2) `fetchPreviousPage()` defaults to `cancelRefetch: true`, so a scroll-fired call could cancel and restart an in-flight delta from another trigger — churn the module-level guard can't prevent, since the scroll handler doesn't go through it. Fix: add an explicit `anchorIndex != null` condition to the scroll handler's `fetchNewerPage` branch (`:512-519`), so it only ever fires for anchored windows, matching its actual purpose (anchored-window backfill). The consolidated trigger effect itself (§3.3) always calls `fetchPreviousPage({ cancelRefetch: false })`, per the Trigger bullet above.
- **`queryFn` branch for `{ resume }`:** `GET /api/conversations/:id?after_index=<resume>&msg_limit=80`. **No `If-None-Match`** — per the streamer's `after_index` contract, the server always returns `200` for `after_index`/anchored windows regardless of a matching conditional header (`server.ts` ~line 1735); sending `If-None-Match` here would be misleading dead code. ETag/`If-None-Match` remains real only for tail-page (`pageParam === -1`) fetches.
- **"Nothing new" is an empty-200, not a 304:** the server returns `200` with `messages: []` when there's nothing past the cursor. An empty page must not stay in the cache — a "no-op merge" isn't a real mechanism here: React Query's `useInfiniteQuery` always prepends whatever the `queryFn` returns to `pages`/`pageParams` on a resolved `fetchPreviousPage()`, with no supported way for the `queryFn` to decline; there is no point before the fetch resolves where an empty result is knowable. **Mechanism: strip-after-resolve.** After `fetchPreviousPage()` resolves, if the just-prepended first page has `messages.length === 0`, remove it surgically via `queryClient.setQueryData` (drop `pages[0]` and its matching `pageParams[0]`) — this never touches message content, it only removes the empty husk RQ just wrote. This lives in the same trigger effect that runs the drain loop (next bullet): that effect already inspects the resolved page's `message_pagination` to decide whether to continue draining, so it observes `messages.length` for free and can strip in the same pass.
- **Non-empty `200`** → merge the returned messages onto the existing cached pages (append — this is newer-than-cursor content by construction) and let the derived cursor naturally advance on next read (since it's `max(message_index)` over cache contents, no explicit "advance" step needed).
- **Cursor validity check:** before treating a non-empty `200` response as a valid delta, check `message_pagination.total <= lastMessageIndex` (note `<=`, not `<`: `message_index` is 0-based, so a message at index N exists iff `total >= N + 1`; `total == lastMessageIndex` means the cursor points one past the new end — e.g. a single-message truncation — and must also be treated as invalid, not merged). If invalid, discard the cached tail query data entirely (`queryClient.removeQueries` for that key) and re-fetch from `-1`. Once streamer PR 2 ships, a `message_pagination.etag` mismatch (not present in the current contract, additive field) triggers the same discard-and-refetch path. Server never silently serves a wrong delta onto stale local history. **This check runs on every drain iteration, not just the first** — a truncation happening mid-drain (e.g. the file is rewritten between the 1st and 2nd of 3 sequential pages) must abort the whole drain into the discard-and-refetch path immediately, not merge the still-valid-looking first page and then silently stop.
- **No cursor** (fresh install, or history was GC'd/discarded) → `initialPageParam` is `-1`, unchanged tail-fetch behavior.

### 3.3 Retry hygiene (item 4) — and consolidating all triggering into `useConversation`

- `useConversation`'s query moves off `staleTime: 0` (inherited from the global default) to an explicit `staleTime: 15_000`.
- **Automatic refetch triggers must be disabled for this query**, not just throttled by `staleTime`. `useInfiniteQuery` refetch replays every cached page in the chain sequentially; with item 1's 7-day-durable pages, that chain is long-lived, and the default `refetchOnMount: true` / `refetchOnWindowFocus: true` / `refetchOnReconnect: true` would still fire a full sequential page-chain replay on any mount/focus/reconnect that lands more than `staleTime` (15s) after the last fetch — exactly the "re-download history the device already has" behavior the design forbids, and it would make acceptance test 1 (first network call is the `after_index` GET) fail on any open more than 15s after the last one. Set `refetchOnMount: false`, `refetchOnWindowFocus: false`, `refetchOnReconnect: false` on this query.
- **All delta triggering is owned by `useConversation`, not `useConversationStream`.** `useConversationStream` (mounted separately, inside `LiveConversationView`, `components/conversation/LiveConversationView.tsx:85`) has no reference to a `useConversation` instance's `fetchPreviousPage` handle, so it cannot itself be the caller — the two are independent hook instances, possibly with `useConversation` mounted in a parent screen and `useConversationStream` in a child. Resolution: `useConversationStream.ts` sheds all three of its `invalidateQueries` call sites (`:72` subscribe, `:90` `connected`-transition, `:102` `running→not-running`) and stops touching the conversation query cache entirely — it becomes purely the live-overlay hook (parse WS lines, `seenIds`, expose `liveMessages`). `useConversation` instead observes WS status directly, as an **observer, never an owner**: it subscribes to the existing per-`serverId` WS client (the same `wsManager`-backed stream `useConversationStream` already reads), filtered to `connected` transitions and this conversation's `running→not-running` transition. If no socket exists for the server, the subscription is inert — `useConversation` never creates or manages a connection. One effect inside `useConversation` now triggers the delta fetch (§3.2) from four sources: mount, `AppState` foreground, WS `connected` transition, and `running→not-running` transition.
- **Guard state is module-level, keyed by `queryKey`, not per-hook-instance.** `useConversation` can be mounted multiple times concurrently for the same conversation (e.g. detail screen + preview sheet, acceptance criterion 6) — a per-instance ref would let each mounted instance independently fire within the same window, defeating the guard. Use a module-level `Map<queryKeyHash, lastTriggeredAt>` (same pattern as the existing `firstPageEtags` map) so all instances observing the same conversation share one throttle: skip the trigger if the last one for this `queryKey` was under 5s ago. In-flight dedup for concurrent instances comes free from React Query itself (same `queryKey` → shared query state, `isFetchingPreviousPage` is already query-level, not per-mount). **The guard stamps once per logical trigger, at drain start — not once per drain iteration.** The drain loop (previous section) is one trigger event that happens to issue several sequential `fetchPreviousPage()` calls; if each iteration re-stamped `lastTriggeredAt`, the 5s guard would block its own continuation fetches (each iteration typically resolves in well under 5s). Stamp before the first fetch of a drain, not before each one.
- Every trigger call is `fetchPreviousPage({ cancelRefetch: false })` (§3.2's Trigger bullet) so it never self-cancels a fetch already in flight from another source.
- **Coverage note:** because the trigger now lives in `useConversation` rather than `useConversationStream`, it fires for *any* mounted consumer of the conversation query — including the read-only detail screen when `LiveConversationView` isn't mounted at all. This is a strict improvement over today, where the `invalidateQueries` calls only ever fired while `LiveConversationView` (and therefore `useConversationStream`) was mounted.
- **`refetchOnMount: false` does not suppress the cold-mount initial fetch.** It only suppresses refetch of *already-cached* data; a query with no cached data still runs its normal fetch on mount regardless of this flag or of whether the WS-driven trigger paths exist. So a conversation with no cursor yet gets its first tail fetch exactly as it does today — nothing about consolidating the trigger changes that path.
- Keep the existing 8s/15s `AbortController` timeouts unchanged (item 4 explicitly says keep them).
- Item 3 (WS resume-by-seq, follow-up PR) changes what data the WS overlay carries (`seq` → real `message_index` on live messages, consumed by §3.4's merge), not this fetch/trigger mechanism — the consolidated trigger in `useConversation` is already the final shape; item 3 doesn't need to touch it again.

### 3.4 Id unification (item 5)

`LiveConversationView`'s merge (`components/conversation/LiveConversationView.tsx:87-111`) moves from uuid-only dedup to a `(message_index, uuid)`-aware merge, with these rules:

- **uuid remains primary** for dedup — this PR does not change today's actual dedup behavior, because WS-parsed live messages don't carry `message_index` yet (that arrives with streamer PR 2's `seq` field, consumed in the follow-up PR). This PR establishes the merge-key *contract* and the persistence boundary below; the WS-resume PR later starts feeding real indexes into an already-correct merge.
- **Ordering is tiered:** when both sides of a comparison have a `message_index`, order by index. When either side lacks one (all WS live messages, today), fall back to today's arrival-order-after-history placement. No interpolation or synthetic index assignment.
- **Persistence boundary (new invariant this PR introduces):** index-less WS messages must never be written into the persisted query cache and must never advance the derived cursor (§3.1). They stay in the render-time live overlay exactly as today. A live message only enters durable storage once the next `after_index` delta fetch (§3.2) returns it with a real server-assigned `message_index`. This keeps "cursor = max index over server-indexed cached messages" true at all times — the cursor is never fed a client-guessed index.

## 4. Error handling

- **Cursor invalidation:** `total <= lastMessageIndex` on a delta response → discard cached tail history + implicitly the derived cursor (no history = no cursor), refetch tail from `-1`. Never merge a delta onto history that might not be its true predecessor.
- **Empty-200 on delta:** RQ prepends the empty page as it resolves, then the trigger effect strips it via `setQueryData` in the same pass (§3.2's strip-after-resolve mechanism) — net effect is no page left in the cache, no further requests (acceptance criterion 2; see §3.2 — this endpoint never returns 304). `hasNewerPage` stays `true` afterward (per §3.2, not latched), so the next mount/foreground trigger can check again.
- **Network failure on delta fetch:** falls through to React Query's existing `retry: 0` / error-state handling — the locally-rendered cached data stays visible (already satisfies "renders instantly" even if the delta fetch fails); no special-casing needed beyond what `useInfiniteQuery` already does for query errors.
- **ETag map corruption/missing on read:** treated as "no known ETag" — plain fetch without `If-None-Match`, matching existing graceful-degradation behavior for `firstPageEtags` (`useConversations.ts:412-413`). The AsyncStorage hydration read is async, so a tail fetch that races module init before the map is hydrated behaves the same way (fetches without `If-None-Match`, gets a 200 instead of a possible 304) — accepted as benign, not a correctness issue.

## 5. Testing strategy

Existing suites to extend: `__tests__/unit/hooks/useConversations.test.tsx` (gains all delta-trigger, cursor, and guard coverage — WS-status-driven triggering included, since that logic moves here per §3.3), plus `LiveConversationView`'s existing test file for merge-key changes. `__tests__/unit/hooks/useConversationStream.reconnect.test.tsx` and `useConversationStream.statusRefetch.test.tsx` shrink accordingly: their `invalidateQueries`-assertion cases move to `useConversations.test.tsx`, and what remains there should assert `useConversationStream` no longer touches the conversation query cache at all (no `invalidateQueries` calls survive in that hook post-refactor).

Acceptance criteria (from the session prompt) map to tests as follows:

1. **Cold relaunch renders from disk, delta carries `after_index=<cursor>`, zero network before it** — mock a rehydrated persisted cache with a tail page present, mount `useConversation`, assert cached data renders before any network call resolves, assert the mount-triggered `fetchPreviousPage()` issues `GET ?after_index=<cursor>` as the first (and with `refetchOnMount: false`, only) network call — no preceding tail-fetch call.
2. **Background→foreground, exactly one delta request, empty-200 → stripped / no re-render churn / no further requests** — drive an `AppState` foreground transition, assert one `after_index` GET with no `If-None-Match` header, mock a `200` with `messages: []`, await the trigger effect's strip-after-resolve pass, assert `pages.length` is back to its pre-fetch count (the empty page RQ momentarily prepended is removed, not merely "never added"), assert no second request fires, assert a *second* foreground transition later still issues a fresh delta request (proves `getPreviousPageParam` isn't latched shut after an empty result).
3. **New messages merge exactly, no dup by uuid, ordered by index, cursor advances** — mock a non-empty `200` delta with N new messages, assert merged page list, assert derived cursor (`max(message_index)`) reflects the new max. **Drain case:** mock a 200-message backlog as 3 sequential `after_index` pages (`has_more_newer: true, true, false`), assert exactly 3 sequential `after_index` GETs fire from one trigger, assert the full 200 messages land in the merged cache with no gap, assert the module-level guard is stamped once (not 3 times) for the whole drain.
4. **`total <= lastMessageIndex` discards + refetches tail (including the `total == lastMessageIndex` boundary)** — mock a delta response with `total` equal to, and separately below, the local cursor, assert both trigger `removeQueries`/refetch-from-`-1`, assert no merge occurred in either case.
5. **WS flap ×5/10s → ≤1 delta fetch, zero full-tail refetches** — mount `useConversation`, drive 5 WS `connected` transitions within 10s on the observed status stream (fake timers), assert the delta trigger (`fetchPreviousPage`/`after_index` GET) fires once (module-level guard holds across the mounted instance) and assert zero calls to `invalidateQueries` for the conversation key and zero tail-page (`pageParam === -1`) fetches across all 5 transitions. Separately assert `useConversationStream`, mounted alongside, makes no query-cache calls of its own for the same sequence.
6. **Same-key consumers (detail + preview sheet) → one in-flight request** — mount two consumers of the same `queryKey` concurrently, assert one network call (React Query dedup + `staleTime: 15s`).

Additionally: unit test for the ETag AsyncStorage read/write round-trip (hydrate on init, debounced write on set/delete), and a `gcTime` assertion that anchored-window queries retain the 5-minute default while the tail query gets 7 days.
