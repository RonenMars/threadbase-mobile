# i18n Implementation Design

**Date:** 2026-05-02  
**Status:** Approved

## Context

tb-mobile has ~130 components and 8 screens with all user-facing strings hardcoded inline — no i18n infrastructure exists. The goals are: (1) ship to international users, (2) establish clean infrastructure for future languages, and (3) meet locale compliance requirements. Hebrew (RTL) is on the near-term roadmap. Translations will be dev/AI-managed, not via an external TMS.

## Decision

Use **i18next + react-i18next + expo-localization**. Industry standard for React Native, best ecosystem support for AI-assisted translation, built-in plural/interpolation, RTL-ready. Launch with English only; locale detection at app startup; Zustand stores the locale so runtime switching can be added later without restructuring.

## Architecture

### Packages

```
i18next
react-i18next
expo-localization
intl-pluralrules   (polyfill for older Android)
eslint-plugin-i18next  (added after Wave 5)
```

### File Layout

```
locales/
  en/
    common.json       # shared: buttons, errors, loading states
    sessions.json     # session list, cards, status, sort/filter
    settings.json     # settings screen labels, notification strings
    servers.json      # server management modals
    terminal.json     # session detail, action sheets, alert dialogs
    onboarding.json   # onboarding flow + browse + conversation screens
  he/                 # Hebrew (future — same structure)
lib/
  i18n.ts             # i18next init + locale detection
  i18n.types.ts       # TS module augmentation for all namespaces
```

Within each JSON file, keys are nested objects (not flat strings):

```json
// sessions.json
{
  "card": {
    "status": { "active": "Active", "waiting": "Waiting for Input" },
    "connectedTo": "Connected to {{server}}"
  },
  "list": {
    "sessionCount_one": "{{count}} session",
    "sessionCount_other": "{{count}} sessions",
    "empty": "No sessions"
  }
}
```

### Initialization Flow

1. `_layout.tsx` boots → calls `lib/i18n.ts`
2. `expo-localization` detects device locale
3. `i18next.init()` sets language (falls back to `en` if no translation exists)
4. Zustand `useSettingsStore` stores the active locale (enables future switching)
5. `I18nextProvider` wraps the app tree

### RTL Readiness

```ts
// lib/i18n.ts — wired now, activates when Hebrew is added
import { isRTL } from 'expo-localization';
import { I18nManager } from 'react-native';
I18nManager.forceRTL(isRTL);
```

### Usage Pattern in Components

```tsx
const { t } = useTranslation('sessions');

// Static
<Text>{t('card.status.active')}</Text>

// Interpolation
<Text>{t('card.connectedTo', { server: name })}</Text>

// Plural
<Text>{t('list.sessionCount', { count })}</Text>

// Imperative (alerts, notifications — outside React tree)
Alert.alert(i18n.t('terminal:dialog.cancelTitle'));
```

## TypeScript Integration

`lib/i18n.types.ts` augments the i18next module to derive types directly from the English JSON files:

```ts
import type common from '../locales/en/common.json';
import type sessions from '../locales/en/sessions.json';
// ...

declare module 'i18next' {
  interface CustomTypeOptions {
    defaultNS: 'common';
    resources: {
      common: typeof common;
      sessions: typeof sessions;
      settings: typeof settings;
      servers: typeof servers;
      terminal: typeof terminal;
      onboarding: typeof onboarding;
    };
  }
}
```

This gives: key autocomplete, compile-time typo errors, and interpolation variable type checking. No manual type maintenance — add a key to JSON and TypeScript picks it up automatically.

## String Extraction: 5-Wave Migration

Each wave ships independently. The app stays functional throughout — untouched components keep hardcoded strings until their wave.

| Wave | Namespace(s) | Key Files | ~Keys |
|------|-------------|-----------|-------|
| 1 | Infrastructure + `common` | `lib/i18n.ts`, `lib/i18n.types.ts`, `_layout.tsx`, `components/ui/*`, `components/shared/*` | ~15 |
| 2 | `sessions` | `components/sessions/*`, `app/index.tsx` | ~40 |
| 3 | `terminal` | `app/session/[id].tsx`, `components/terminal/*` | ~25 |
| 4 | `servers` + `settings` | `app/settings.tsx`, `components/servers/*` | ~35 |
| 5 | `onboarding` + remaining | `app/onboarding.tsx`, `app/browse.tsx`, `app/conversation/*` | ~20 |

**Total: ~135 keys across 6 namespaces**

### Special Cases

| Case | Handling |
|------|----------|
| Alert / ActionSheet strings | `i18n.t()` directly (imperative API, outside JSX) |
| Notification content | `i18n.t()` directly (called from `services/`) |
| Accessibility labels | Regular string extraction, key suffix `.a11y` |
| Slash commands / session IDs | **Not extracted** — technical identifiers stay hardcoded |

### Lint Guard (added after Wave 5)

`eslint-plugin-i18next` warns on raw JSX string literals:

```tsx
<Text>Cancel Session</Text>   // ⚠ ESLint warning
<Text>{t('terminal.cancelSession')}</Text>  // ✓
```

## Testing

### Setup

`jest.setup.ts` imports `test-utils/i18n-test-setup.ts`, which initializes i18next with real English translations (not key stubs). Existing assertions like `getByText('Active')` keep working unchanged.

### Test Utility

```tsx
// test-utils/render.tsx
export function renderWithI18n(ui: ReactElement) {
  return render(
    <I18nextProvider i18n={i18n}>{ui}</I18nextProvider>
  );
}
```

Components migrated to use `useTranslation()` are rendered via `renderWithI18n` in tests.

### New Tests

1. **Key completeness** — when a second locale is added, assert all English keys exist in the new locale (CI guard against missing translations)
2. **Plural forms** — `t('sessions.list.sessionCount', {count: 1})` → `"1 session"`, `{count: 3}` → `"3 sessions"`
3. **Locale switch** (skipped until runtime switching is implemented) — assert Zustand locale change triggers re-render with new strings

### CI Impact

The existing 265-test Jest suite stays green throughout migration. Each wave's PR is independently testable. No test rewrites — only add `renderWithI18n` wrapper as components are migrated.
