# Threadbase Pain Points — Effort & Complexity Matrix

Source list: [`threadbase-disadvantages-and-pain-points.md`](../../threadbase-disadvantages-and-pain-points.md).

Scored against the **current** `integration-dev/v1.0.0-2026-07-22` branch of both repos: `tb-mobile` @ `33ecfc3` and `tb-streamer` @ `3b971fb`. Every score was re-verified by reading the actual files in full (not excerpts) and adversarially hunting for edge cases and hidden complications — several first-pass scores moved as a result (see [Revision log](#revision-log)).

**Effort** = how much new work is needed. **Complexity** = how architecturally hard that work is (single-file tweak vs. cross-system redesign). **Pain** = how visible/damaging it is to the end user *right now* — independent of how hard it is to fix.

- **Effort / Complexity:** 🟢 Small · 🟡 Medium · 🔴 Large.
- **Pain (user-facing severity):** 🔥🔥🔥 Severe — breaks the core promise or a trust anchor; the user hits it on the main path and either can't proceed or stops believing the app. 🔥🔥 High — frequent friction or a visible trust dent on a common path. 🔥 Moderate — noticeable but avoidable, or only on a secondary path. 💤 Latent — real harm, but invisible until it bites (scale, security, data-loss, upstream drift); low felt-pain today, high regret later.
- **Where:** 🖥️ mobile fix · 🛰️ backend (tb-streamer) fix · 🖥️🛰️ both · 🏢 org/strategy, not code.

Sorted by Effort (ascending), then Complexity (ascending) within each tier. **Pain is deliberately orthogonal to the sort** — scan the 🔥🔥🔥/🔥🔥 rows sitting in the 🟢/🟡-effort tiers first; those are the highest-leverage fixes.

## Reading the matrix

- **Genuine quick win (🟢/🟢):** only **#9** truly qualifies now — and even it hides the `activeServerIds[0]` wrong-server fallback to fix first.
- **Bounded, worth scoping (🟡 effort):** #20, #18, #3, #13, #15, #16 — well-understood, but each carries a specific trap called out above (silent-swallow, static-vs-probing, hard-coded resize, non-constant-time pair token).
- **Big but contained (🔴 complexity, 🟡 effort-ish elsewhere):** #22 (dual-DB + creds-outside-DB), #17 (breadth, not redesign).
- **Strategic architecture bets (🔴/🔴):** #2, #7, #6, #5, #1, #8, #12, #21, #14 — the product's core weaknesses. These map almost exactly onto the source doc's own "Most urgent priorities" (durability, core-flow reliability, provider resilience, trustworthy status, security, diagnostics).
- **Not code problems (—):** #23, #24, #19 — product/business decisions, no PR.

## Pain vs. effort — where to spend

The Pain column is orthogonal to Effort on purpose. Read the two together to prioritize:

- **Do first — high pain, low-ish effort (the leverage zone):**
  - **#18 Notifications (🔥🔥🔥 / 🟡)** — the source doc calls push "the main reason I installed the app," yet failures are silently swallowed today. Highest pain-to-effort ratio on the board. A test-send + delivery-health surface is self-contained mobile work.
  - **#20 Diagnostics (🔥🔥 / 🟡)** — the screen already exists; turning the static dump into real per-layer probes directly answers "I don't know whether it's the phone, network, tunnel, streamer, or agent." High felt-pain exactly at the moment of failure.
  - **#3 Onboarding polish (🔥🔥 / 🟡)** — first-run friction is where users churn; this is copy/IA, not architecture.
  - **#9 Multi-server (🔥 / 🟢)** — genuinely cheap; fix the `activeServerIds[0]` wrong-server fallback while you're there.
- **Must do, but expensive — severe pain, large effort (the strategic core):** **#1 durability (🔥🔥🔥)**, **#2 core-flow reliability (🔥🔥🔥)**, **#11 zero-config remote (🔥🔥🔥)**, **#13 trustworthy status (🔥🔥🔥)**. These are the promises the product is *sold on*; they're 🔴 effort and unavoidable. #13's mobile half is cheap, but true reliability is capped by CLI opacity — manage expectations, don't just add heuristics.
- **Latent landmines — low pain now, high regret later (schedule before they bite):** **#16 security (💤)**, **#22 backup/data-loss (💤)**, **#17 permissions (💤)**, **#12 provider drift (💤 → sudden 🔥🔥🔥 on the next Claude/Codex release)**. Zero felt-pain today is exactly why these get deferred until an incident. #12 especially: it's invisible right up until an upstream TUI restyle silently breaks status/question detection for everyone at once.
- **Grade-on-a-curve pain (context-dependent):** **#6 providers** and **#21 search** are 🔥 for today's Claude/Codex + small-history users and 💤 for adopters/heavy users — the felt-pain rises with the user's history size or the next agent they adopt.

**One-line takeaway:** spend the next cheap cycles on **#18 → #20 → #3 → #9** (high pain, contained), keep grinding the 🔴 strategic core (**#1, #2, #11, #13**) that the product's value depends on, and schedule the 💤 landmines (**#16, #22, #12**) *before* the incident that turns them 🔥.
